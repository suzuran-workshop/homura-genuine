# PRD — homura-genuine（中央授权服务）

## 产品目标

让"散布出去的 AI 生成轻应用"的**制作人**保留运行控制权：即使产物已经落到别人的部署环境里，
也能远程调到期、按持有者分功能、必要时即时停服——并且**授权本身不可被产物持有者篡改**。

## 用户与使用场景

**目标用户**：homura 系列轻应用的制作人（一方运营）。不是终端用户，也不是 App 本身——
App 是消费侧，制作人是决策方。

**典型场景**：

1. **限时试用转付费**：给试用者签 30 天许可；到期前 3 天调 `notice` 让 App 每次响应带
   续期提醒；到期日一到，中心不改任何字段——消费侧本地判定就会自动切到 `expired`，
   按 `enforcement` 处置。付费后 PATCH `expiresAt: null` 转永久。
2. **按持有者分功能**：同一份产物散给多人，通过 `features` 数组给不同人开不同能力；
   App 侧用 `requireFeature(client, 'export')` 逐路由闸门。签名保证持有者不能给自己加功能。
3. **紧急停服**：发现某持有者违规、或产物存在严重 bug 需要停用，PATCH `status: suspended`
   - `enforcement: all`，下一次心跳（10 秒~5 分钟）即全站 503。豁免路径（`/_license`、
     健康检查、登录链）仍可读，前端能解释"为什么停了"。
4. **密钥轮换**：怀疑签名私钥泄露或到轮换周期，POST `/admin/keys/rotate`：旧钥退休
   （历史签名仍可验，`GET /v1/keys` 会返回退休钥），新钥立即接管签发。持有旧公钥的
   App 会看到 `signature.kind: invalid` 并触发最严处置——**这是故意的**：强制 App
   运营方更新公钥配置，避免旧钥被继续信任。
5. **观察期**：不确定新处置规则会不会误伤，先 `enforcement: none` + `status: suspended`
   让 App 记录但不拦，观察一段再收紧到 `notice`/`core`/`all`。

## 核心问题

**产物落在别人手里，怎么保留控制权？**

三条常见路都不通：

- **对称密钥签名**：密钥必须随产物分发，拿到产物即可自签"永不过期 + 全功能"，等于没有控制
- **每次操作都在线校验**：网络抖动 = 全站宕机；且离线部署（内网/边缘）根本走不通
- **信任 App 自我约束**：产物持有者可以改 App 代码或拦响应，任何在 App 侧的判断都可绕过

只有**非对称签名 + 本地验签 + 短周期心跳**能同时满足：授权不可篡改（私钥不出中心）、
网络失联可容忍（宽限期内 fail-open）、控制可远程即时生效（心跳周期内翻新）。

## 功能及其意义

| 功能                                                  | 解决什么                                      | 为什么需要                                                                             |
| ----------------------------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------- |
| 许可证签发（`POST /admin/licenses`）                  | 把授权落到具体 `(product, app, licenseKey?)`  | 没有签发就没有可分发的东西                                                             |
| 自助注册（`allowSelfRegister` + `POST /v1/register`） | 让 App 首次启动即拿到默认授权，无需中心手动签 | 面向"散布到不特定人"的场景；配合 `defaultTtlDays`/`defaultFeatures` 就是"试用即开即用" |
| 实例绑定（`instanceKey`）                             | 一张许可只跑一个实例                          | 防止把 A 实例的授权响应重放给 B 实例；关闭自助注册时是"一份授权一个部署"的硬约束       |
| 到期控制（`expiresAt` + 消费侧本地判定）              | 到点自动降级，无需中心在线                    | 消费侧本地判定不依赖当次心跳——即使中心宕机，到期也照样生效                             |
| 处置强度（`enforcement: none/notice/core/all`）       | 分级处置，可先观察后收紧                      | 直接全站停太重；只提醒又太轻。四档让运营按情境选                                       |
| 功能范围（`features[]`）                              | 按持有者开不同能力                            | 同一份产物散给多人时唯一的分权手段；签名保证不可自加                                   |
| 强提醒文案（`notice`）                                | 中心可自定义提醒；不写时消费侧自动生成        | "无差别提示所有用户"是硬要求，不能依赖运营记得填                                       |
| 即时停服（`status: suspended`）                       | 心跳周期内全站 503                            | 违规处置与紧急止损的唯一手段                                                           |
| 心跳（`POST /v1/heartbeat`）                          | 消费侧短周期拉最新签名授权                    | 中心侧任何调整都要通过心跳下发；`serverTime` 顺带校正消费侧时钟偏差                    |
| Ed25519 签名（`signEntitlement`）                     | 授权完整性                                    | 支点是"非对称"——App 侧只有公钥，改任何字段都会验签失败                                 |
| 密钥轮换（`POST /admin/keys/rotate`）                 | 私钥泄露或到周期时换新                        | 旧钥退休后仍可验历史签名（`GET /v1/keys` 返回退休钥），避免轮换期消费侧集体验签失败    |
| 管理端点强鉴权（Bearer token）                        | 未配 token 时 `/admin/*` 整体 503             | 绝不降级为匿名可管；宁可不开放，不可裸奔                                               |
| 时钟偏差防护（`serverTime`）                          | 用户回拨系统时间绕过到期                      | 消费侧用 `serverTime` 校正本地判定，回拨无效                                           |

## 功能之间的关系

- **签发 → 绑定 → 心跳 → 调整**是一条主线：`POST /admin/licenses` 或 `POST /v1/register`
  创建许可（后者会绑 `instanceKey`）；`POST /v1/heartbeat` 短周期刷新；`PATCH /admin/licenses/:id`
  随时调整任何字段
- **签名贯穿所有下发**：`register`/`heartbeat` 的响应都带 `SignedEntitlement`（载荷 + 签名 + keyId），
  消费侧本地验签后才采信载荷
- **状态 vs 处置 vs 文案**三层分离：`status` 说"发生了什么"，`enforcement` 说"该拦多少"，
  `notice` 说"怎么告诉用户"。三者都由中心控制、可独立调整。`active` 时 `enforcement` 恒为
  `none`（不给消费侧留误拦余地）；非 active 时 `notice` 缺省会自动生成（不依赖运营记得填）
- **有效状态是算出来的**：`manualStatus`（active/suspended/revoked）+ `expiresAt` + `now` →
  `effectiveStatus`（active/suspended/expired）。不存 DB，避免"随时调整期限"出现存算不一致

## 范围与非目标

**范围内**：

- 许可证签发、查询、调整、绑定实例
- 到期时间、功能范围、处置强度、提醒文案的中心控制
- Ed25519 签名下发与密钥轮换
- 心跳协议（含 `serverTime` 时钟偏差校正）
- 管理端点强鉴权（Bearer token）

**非目标**（明确排除）：

- **不做**用户身份/登录/OAuth：那是 `../oauth2-dingtalk` 的职责
- **不做**业务数据托管：App 自己的业务数据在 App 那边（或它自己的 supabase），中心不接管
- **不做**多租户组织模型：产品是"扁平"的，没有组织/团队/角色层级。要区分持有者靠
  `features` 数组，不靠组织树
- **不做**计费/支付：到期时间是运营手动或外部系统 PATCH 进来的，中心不对接支付网关
- **不做**产物分发：产物在哪、怎么发是 App 制作人的事
- **不做**消费侧的处置执行：中心只签发授权，具体拦哪些路径、返回什么状态码、UI 怎么展示，
  都由 `../homura` 的 `@homurajs/license` 决定
- **不做**高可用/水平扩展：单进程 + 单 sqlite 文件是当前设计上限。要 HA 得先解决私钥
  托管与 sqlite 复制，那是另一个项目
